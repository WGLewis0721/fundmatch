# n8n research for FundMatch

## What it is

n8n is a workflow-automation platform that combines app/API integrations with code and AI nodes. It supports AI agents, vector stores (including Supabase/PGVector), MCP client tooling, sub-workflow tools, human fallback/review patterns, execution history, and retries.

Primary sources:

- https://docs.n8n.io/
- https://docs.n8n.io/workflows/executions/all-executions/
- n8n Advanced AI documentation and AI Agent / vector-store nodes under the official docs navigation

## Where it fits

n8n is strongest at integration-heavy automation around FundMatch rather than the core matching/intelligence engine.

Good future uses:

- receive partner webhooks and normalize them before calling FundMatch APIs;
- sync approved records to/from CRM systems;
- trigger controlled emails or Slack notifications;
- scheduled data imports;
- operator workflows for failed jobs;
- pilot-era integrations that would be expensive to custom-code immediately.

## Why it should not be the core runtime

The core FundMatch decision path needs code-reviewed authorization, deterministic eligibility, versioned prompts/models, source-level provenance, typed schemas, and business-level audit records. Putting the primary matching loop inside a visual automation graph would split core business logic between the repository and an external workflow system.

That would make testing, deployment, change review, and IP control worse.

## Useful n8n capabilities

### AI Agent + tools

n8n can expose app nodes, custom code, other workflows, MCP tools, and retrieval to an AI agent. This is useful for internal operations and experiments.

### Human-in-the-loop

n8n can pause before selected tool calls/actions for review. This is suitable for operational workflows such as sending outbound communications or resolving integration exceptions.

### Execution history/retry

Execution history is useful for operator visibility and replay of integration workflows. It is not a replacement for FundMatch's own `agent_runs`, `agent_steps`, and marketplace events.

## Decision

**Keep n8n outside the core agentic RAG runtime. Use it as an optional integration/operations adapter after the core FundMatch APIs and MCP/service boundaries are stable.**

If n8n is adopted, workflows should call FundMatch's server endpoints rather than connect directly to private tables with broad credentials.

## Guardrails

- no direct service-role database credential in shared visual workflows;
- no proprietary matching weights/prompts copied into n8n;
- no canonical company/profile writes without using FundMatch's validation/review API;
- no unreviewed outbound founder/investor communication generated by an agent;
- keep external workflow execution IDs on integration audit records for traceability.
