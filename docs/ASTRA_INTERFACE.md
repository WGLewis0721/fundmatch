# Interfaces for Astra: uploads, processing status, profile updates

Astra owns deck extraction, sourced profiles, matching explanations and
readiness suggestions. This document defines the identifiers and the
authorized write paths those features use. Everything below is created by
`drizzle/migrations/0002_fundmatch_accounts_persistence.sql`.

## Identifiers

| Identifier               | Type                                         | Where                        | Meaning                                                                                    |
| ------------------------ | -------------------------------------------- | ---------------------------- | ------------------------------------------------------------------------------------------ |
| `documents.id`           | uuid                                         | `public.documents`           | The **upload id**. Generated by the client before upload; stable for the life of the file. |
| `documents.org_id`       | uuid                                         |                              | Owning organization. All authorization derives from it.                                    |
| `documents.startup_id`   | uuid, nullable                               |                              | Company the document belongs to (set for founder uploads).                                 |
| `documents.storage_path` | text                                         |                              | Object key in the private `documents` bucket: `<org_id>/<document_id>/<file_name>`.        |
| `documents.uploaded_by`  | uuid                                         |                              | `auth.users.id` of the uploader.                                                           |
| `documents.kind`         | `deck` \| `financials` \| `legal` \| `other` |                              | Founder-declared type.                                                                     |
| `profile_suggestions.id` | uuid                                         | `public.profile_suggestions` | One proposed field change.                                                                 |
| `readiness_items.id`     | uuid                                         | `public.readiness_items`     | One checklist row; `item_key` is stable per template (`Company-0`, `Financials-1`, ...).   |

## Upload lifecycle and `documents.status`

```
pending ──(client upload + mark_document_uploaded)──▶ uploaded
uploaded ──(worker: set_document_processing 'processing')──▶ processing
processing ──▶ processed   (extraction jsonb stored, processed_at set)
processing ──▶ failed      (processing_error stored)
```

1. The app inserts the `documents` row with `status = 'pending'` (RLS: member
   of `org_id`, `uploaded_by = auth.uid()`), uploads the bytes to
   `storage_path`, then calls `mark_document_uploaded(document_id)`, which
   verifies the object exists and moves the row to `uploaded`.
2. Astra's worker polls or subscribes for `status = 'uploaded'` (partial index
   `documents_status_idx` covers it), then calls, with the **service role**:

   ```sql
   select public.set_document_processing('<document_id>', 'processing');
   -- ... extract ...
   select public.set_document_processing('<document_id>', 'processed', null, '{"funding_ask": 3000000, "pages": 14}'::jsonb);
   -- or
   select public.set_document_processing('<document_id>', 'failed', 'Could not parse PDF');
   ```

   `set_document_processing` is executable only by `service_role`. It refuses
   `pending` rows and only accepts `processing`, `processed`, `failed`.

3. Authenticated users can change only `kind` and `startup_id` on a document
   (trigger `documents_guard`); `status`, `extraction`, `processing_error`,
   `processed_at` are worker-owned.
4. Reading the bytes: the worker uses the service role with the Storage API
   (`storage.from('documents').download(storage_path)`). Never generate public
   URLs; the bucket is private and must stay so.

Uploads are limited to 25 MB and these MIME types (enforced by the table
check, the bucket definition and the client): PDF, PPTX, DOCX, XLSX, CSV,
plain text, PNG, JPEG.

## Authorized profile updates

Astra should not write to `startup_profiles` directly. Instead it proposes
changes that founders accept in the app:

```sql
insert into public.profile_suggestions
  (startup_id, document_id, field_key, label, suggested_value, current_value, confidence, rationale, source_key)
values
  ('<startup_id>', '<document_id>', 'funding_ask', 'Funding ask', '3000000', '2500000', 0.82, 'Slide 12: "Raising $3M seed"', 'fundmatch_ai');
```

Supported `field_key` values:

- Profile columns: `name`, `tagline`, `summary`, `story`, `sector`, `stage`,
  `geography`, `website`, `business_model`, `ai_summary`, `funding_ask`,
  `team_size`, `founded_year`.
- Metrics: `metric:<metric_key>` (for example `metric:arr`, `metric:growth`).
  `suggested_value` is the display value; numeric parsing is attempted for
  `value_numeric`. The MatchEngine reads `metric_key = 'growth'`.

Founders see pending suggestions on the Company profile page and call
`resolve_profile_suggestion(id, accept)`. Accepting applies the value, records
provenance in `source_provenance` (`source_key`, `confidence`, preview) and
marks the suggestion `accepted`. Rejecting marks it `rejected`. Suggestions
are readable only by the startup's organization and writable only by the
service role.

`matches` (score, explanation, strengths, risks, rationale, `generated_by`)
is also service-role-written and readable by both the startup's and the
investor's organizations. The app currently computes fit client-side with the
rules engine; Astra's explanations can be persisted there without schema
changes.

## Readiness suggestions

`readiness_items` rows are created per company and template by
`ensure_readiness_items(startup_id, template)` (templates: `vc`, `pe`). The
worker may, with the service role, update `status`, `notes`, `evidence_url`
and set `suggested_by = 'fundmatch_ai'` on existing rows, or insert
additional rows with a new `item_key`. Keep `org_id = startup_org(startup_id)`.

## Access summary

| Actor                       | Credential                         | Can                                                                                                                |
| --------------------------- | ---------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| Founder/investor in browser | user JWT (publishable key)         | Everything RLS allows for their organizations                                                                      |
| Astra worker                | service role key, server-side only | `set_document_processing`, insert `profile_suggestions`, write `matches`, update `readiness_items`, download bytes |
| Anonymous                   | publishable key, no session        | Nothing (no `anon` grants on application tables or the bucket)                                                     |

The service role key must live only in the worker's environment. It is not
part of the app deployment or any client bundle.
